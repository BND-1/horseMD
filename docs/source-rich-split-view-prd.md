# 源码 + 富文本双栏实时预览 PRD

> 状态：第一版已实现，待扩展真实大文档/人工验收
> 日期：2026-08-04
> 关联：`docs/source-rich-split-view-architecture.md`、`docs/handoff-mode-switch.md`、`docs/markdown-source-preservation.md`

## 1. 要解决的问题

当前 HorseMD 的“富文本”和“源码”是互斥视图：用户需要切换后才能同时确认 Markdown 原文与渲染结果。对写作、调试 Markdown、编写表格/公式/复杂列表的用户而言，频繁切换会打断思路。

新增一个**桌面端双栏预览视图**：

- 左侧：同一文件的 Markdown 源码；
- 右侧：同一文件的富文本预览/编辑器；
- 左侧改动会在短暂合并输入后更新右侧；
- 右侧是只读富文本预览，不接受编辑或富文本右键操作；
- 两侧滚动位置联动，但不会形成互相回跳；
- 打开、浏览、滚动或仅切换视图都不得改写用户源文件。

这不是另存为、比较两个文件或传统 diff 功能，而是**同一份文档的两种同步表达**。

## 2. 产品目标与非目标

### 2.1 目标

1. 让用户在一屏内写 Markdown、立即查看效果。
2. 源码输入在停止连续输入后的短暂延迟内反映到富文本；不能每个字符都强制重建整篇大文档。
3. 富文本编辑后的源码保持与现有“源码保真”策略一致：尽可能只修改用户实际编辑的范围，不擅自规范化空行、列表标记、换行符或转义。
4. 两侧以当前可见内容为锚点进行滚动联动；表格、图片、代码块、长公式等高度不等内容不能依赖简单百分比硬对齐。
5. 保存、关闭、外部文件变更、查找替换、评阅、导出等仍以同一个标签页内容为准，不引入第二份文档状态。

### 2.2 本期非目标

- 不做两个独立文件的对比 / 合并 / diff。
- 不做移动端双栏：小屏空间不足，移动端保持现有单视图与只读模式。
- 不承诺 Markdown 语法错误时的精确诊断器；第一版保证源码不丢失，并提供明确的“预览暂未更新”状态。
- 不把大文件的全量实时解析伪装成无成本能力：重文档必须有性能保护和用户可见的降级策略。
- 不改变既有“富文本”“源码”按钮的语义，也不废弃现有源码/富文本切换路径。

## 3. 用户场景

### 场景 A：写源码并观察效果

1. 用户打开 Markdown 文件，选择“源码 + 预览”。
2. 左侧在标题、列表、表格或 Mermaid 中修改内容。
3. 停止输入约 150–250ms 后，右侧更新为对应渲染；输入法组合输入完成前不抢先刷新。
4. 用户继续在左侧输入，不会因右侧更新而丢失焦点、选区或滚动位置。

### 场景 B：在富文本中编辑，核对原文

1. 用户把光标放在右侧富文本，执行列表转换、表格编辑、评阅等已有能力。
2. 右侧产生的真实用户编辑经现有序列化/保真流程写回左侧。
3. 左侧仅反映该次编辑所必需的源码变化；不会因双栏打开而额外插入空行、把 `-` 改成 `*` 或把用户换行改为 `<br />`。

### 场景 C：长文阅读与定位

1. 用户在任一侧滚动到正文中段。
2. 同侧是“滚动主控”，另一侧跟随到相近的可见段落。
3. 图片、代码块、表格导致两侧真实高度不一致时，目标是**同一语义内容出现在可读位置**，而不是追求两个像素滚动条百分比相同。
4. 用户停止滚动后，两侧不会继续抖动、争夺滚动位置或跳回文首。

### 场景 D：退出双栏

- 从双栏切回“富文本”或“源码”时，以最后有用户交互的一侧作为恢复锚点：有可见光标则跟随光标；阅读状态则保留视口。

## 4. 交互与界面

### 4.1 入口与视图状态

桌面端将文档展示状态扩展为：

- **富文本**（既有）
- **源码**（既有）
- **双栏**（新增：左源码、右富文本）

入口放在富文本编辑区的右键菜单中，使用双栏图标与“源码 + 预览”文字；开启后同一位置显示“关闭源码 + 预览”。快捷键在第一版不强行占用；待自定义快捷键系统中加入命令后再提供默认/可配置方案。

双栏是**每个文档标签独立的显示偏好**，不应影响另一个标签页。重启后的持久化是否纳入第一版，取决于现有 session 设置模型；若实现复杂，第一版可以不持久化，但必须保持当前会话内稳定。

### 4.2 布局

- 左右排列：左为源码、右为富文本；中间有可拖动分隔线。
- 初始比例建议 45% / 55%；每侧最小可用宽度建议 340px。
- 窗口宽度不足时，不压缩到不可编辑：隐藏双栏入口并提示使用单视图，而不是悄悄叠成两栏。
- 原有“两个不同文档并排”的分屏 (`splitId`) 与本功能不同。第一版应避免混用：已有文件分屏开启时禁用双栏入口并解释原因，防止一屏同时出现三/四个编辑面板。
- 左侧源码保持无控制 textarea；右侧使用同一标签已挂载的 Crepe/ProseMirror 实例，不重复创建富文本编辑器。

### 4.3 状态反馈

- 源码输入待渲染时：右侧顶部轻量“正在更新预览”状态，不遮挡编辑内容。
- 源码未能生成可用预览时：左侧继续可编辑、内容可保存；右侧保留最后一次成功预览并显示“预览等待有效 Markdown”的非阻塞提示。
- 任一侧真实编辑后，沿用既有标签脏状态和保存状态；只滚动、切换、同步镜像不得标脏。
- 首次解析大文档、分块加载或 Mermaid/图片资源加载使用既有加载状态，但不能借加载状态把用户输入吞掉。

### 4.4 焦点与命令

- 用户最后点击/输入的面板为“活动面板”。查找、复制、撤销、快捷菜单、右键菜单等默认作用于活动面板。
- 富文本专属能力（表格柄、列表转换、评阅、浮动选区工具条）在双栏右侧全部隐藏；源码侧是唯一编辑面板，保持原生文本编辑行为。
- 双栏右侧的点击、选中、滚动和复制不得产生 dirty 或打开应用右键菜单；左侧修改后，右侧程序化替换不能被误判为富文本用户编辑。

## 5. 内容、保存与数据安全契约

以下约束是第一版不可妥协的验收门槛：

1. 一个标签只存在一份持久 Markdown：`tab.content` / `tabsRef` 是保存、关闭、会话恢复与外部变更处理的唯一提交状态。
2. 左侧 textarea 的 DOM 值不是第二份持久状态；它通过 `liveContentRef` 和原始字节镜像参与保存。
3. 右侧 ProseMirror 文档也不是第二份持久状态；它是富文本投影，必要时通过 `serializerCtx` / `flushMarkdown()` 产生当前 Markdown。
4. 程序化同步必须带来源标记（revision/epoch），禁止“左侧写入 → 右侧 onChange → 左侧 onChange”的循环。
5. `saveTab()`、关闭确认、外部变更判断、导出与源码模式切换均必须先走现有 `getMarkdownForTab()` / `commitAllLive()` 边界，不能读取过期的 React render 值。
6. 不因打开双栏、滚动、预览刷新或退出双栏而修改 Markdown 字节。
7. 现有源码保真约束继续有效：CRLF/BOM、未编辑区域、列表标记、软换行、表格单元格 `<br>`、front matter 等必须按 `docs/markdown-source-preservation.md` 保护。

## 6. 性能与降级

- 源码连续输入应使用合并刷新（首版建议 180ms 左右；IME 在 `compositionend` 后再刷新），不得每个字符全量 `replaceMarkdown()`。
- 富文本右侧使用现有“保持挂载”实例；不允许为双栏再次解析/加载第二个 Crepe。
- 滚动联动采用 `requestAnimationFrame` 合并，每帧最多一次锚点捕获与一次目标恢复；不得在普通 scroll 事件中全篇扫描/全篇测量 DOM。
- 重 Markdown 文档沿用 `heavy` 判定：第一版显示左侧源码并让用户主动“加载富文本预览”；未加载时不承诺实时右侧预览。
- 普通文本文件没有 Markdown 富文本投影，双栏入口隐藏。
- 如果一次源码更新仍在解析时出现下一次更新，旧请求必须可丢弃，仅应用最后版本，避免预览回退。

## 7. 验收标准

### 7.1 同步

- 左侧连续输入、删除、撤销、IME 组合输入后，右侧最终等于左侧最新源码所渲染的内容。
- 右侧预览中的列表、表格、代码块、Mermaid、公式和普通段落均不可编辑；左侧对任意这些 Markdown 结构的修改最终必须在右侧反映，且不出现旧内容复活。
- 双栏同步过程中，脏状态在真实编辑后及时出现；保存、关闭并重新打开后内容一致。
- 打开/关闭双栏、仅滚动两侧、仅拖动分隔线均不产生脏状态。

### 7.2 保真

针对以下样本，未编辑区域在保存/重开后保持原样：

- `-` / `*` / `+` 列表标记和嵌套列表；
- 空行、软换行、段落换行；
- CRLF、BOM；
- 表格、单元格 `<br>`；
- front matter；
- 行内代码与围栏代码；
- Mermaid、LaTeX、图片和本地链接。

### 7.3 滚动与光标

- 左→右、右→左各连续滚动 10 次，目标面板不回到文首、不抖动、不出现无限联动。
- 普通段落、重复文本、标题、表格、图片、代码块、长文中段均能落在相同语义内容附近。
- 两侧任意一边有可见光标时，切换三种视图后光标仍在正确内容处并保持可见；阅读状态则优先保留阅读视口。

### 7.4 回归

至少覆盖：

- `npm run test:source-map`
- `npm run test:issues-105-106-ui`
- `npm run test:list-conversion-ui`
- `npm run test:rich-list-source-ui`
- `npm run test:rich-dirty-indicator-ui`
- Mermaid、PDF、复制、查找替换、外部修改提示的既有针对性回归
- `npm run build` 与 `npm run build:mobile`

文本输入敏感场景必须使用每字符输入的后台 CDP 测试；在 macOS 发布候选阶段还需按 `docs/macos-real-input-testing.md` 做一次真实键盘/鼠标人工回归，但不得抢占用户正在使用的窗口。

## 8. 当前实现范围（第一版）

已落地的范围：

- 桌面富文本编辑区右键菜单新增“源码 + 预览”入口；普通 Markdown 在左源码、右富文本之间并排显示，并可拖动分隔线。
- 两侧复用同一 Tab 的 textarea 与既有 Crepe 实例；不创建第二个 Crepe。
- 左侧连续输入经过 180ms 合并后刷新右侧；IME composition 结束后才刷新。
- 右侧只读，不存在富文本回写；程序化更新和过期 debounce 通过 revision 抑制，避免旧预览覆盖最新源码。
- 两侧滚动采用内容锚点、单侧主控和 rAF 合并；已自动覆盖十次交替方向滚动。
- 查找/替换按最后聚焦面板选择源码或富文本后端；双文档分屏、移动端、纯文本与未显式加载富文本的重文档禁用入口。

实现文件：`hooks/useSplitSourceRichSync.js`、`hooks/useSplitScrollSync.js`、`components/shell/EditorArea.jsx`、`App.jsx`。自动化入口：`npm run test:source-rich-split`。

仍需发布前人工验收：大图片/表格/代码块长文档、中文输入法真实 composition、与 PDF/评阅/外部修改提示组合使用。

## 9. 分阶段实施清单

1. **同步协调器与纯函数测试**：先实现 revision/epoch、程序化写入抑制、输入合并、IME 边界；不改 UI。
2. **双栏结构**：在 `EditorArea` 中复用同一富文本实例与无控制 textarea，新增模式和面板焦点管理。
3. **内容同步**：接通源码→富文本、富文本→源码、保存/关闭/外部修改边界，锁定保真回归。
4. **滚动同步**：基于现有 `scrollAnchor` 做单向主控、rAF 合并、反馈抑制；添加长文/图片/表格样本。
5. **边界集成**：查找替换、评阅、PDF、拆分视图、重文档与无障碍提示。
6. **性能与发布验证**：压力文档、连续输入、重复切换、真实人工测试、指南和更新说明。

任何一阶段出现源码失真、保存滞后、光标漂移或滚动回跳，停止向下一阶段扩展，先补最小复现和回归测试。
