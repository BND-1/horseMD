# 云同步：现状、测试结果、业界做法与改进路线

> 建立：2026-10-29。用途：作为同步功能后续迭代的总文档，每做完一项就更新「迭代记录」和对应条目的状态。
> 相关：[`cloud-sync-v2-prd.md`](./cloud-sync-v2-prd.md)（v2 的方向与安全规则）、[`cloud-sync-v2-architecture.md`](./cloud-sync-v2-architecture.md)。

## 0. 起因

一位用户的建议（原话摘要）：

1. **科技服务于人**：同步对用户应该是无感的，用户只需要知道成功或失败；不应该一有删除就让用户确认，不是每个用户都是 IT 从业者。
2. **数据比一切重要**：编辑功能可以慢慢完善，数据丢了就是丢了。同步要无感，数据保障可以用类似「快照 / 版本」的功能来恢复（思源笔记就是这样）。

结论先行：HorseMD 现在的安全感来自**执行前让用户确认**；成熟产品的安全感来自**执行后一切可撤回**。要做到上面两点，需要先补上「可撤回」（版本历史、最近删除），再去掉确认对话框。

## 1. 现在是怎么做的（读代码，2026-10-29）

### 1.1 用户看到的流程

- 入口只在「设置 › 云同步」（`components/settings/SyncSettings.jsx`）：建连接（WebDAV / S3）→ 绑定文件夹。
  - 第一台设备「上传本地到云端」；第二台设备选已有云端工作区「从云端下载到本地」（一次性的方向操作）。
  - 之后「双向同步」：没有删除和冲突就直接执行；有就先列出每个文件的操作，确认后执行。
- 自动同步（`hooks/useAutoSync.js`）：`settings.syncAutoMinutes` 默认 **0（关闭）**，可选 5 / 15 / 30 / 60 分钟。
  - 只上传和下载；计划里有任何删除或冲突，**整轮不执行**，提示用户去设置里确认（`safeOnly` → `needsConfirmation`）。
  - 只同步已保存的内容；自动保存 `settings.autoSaveDelay` 默认也是 **0（关闭）**。
- 同步状态只在设置页显示。状态栏、侧边栏看不到同步成功或失败。

### 1.2 引擎（`src/main/sync/`）

- **云端**：`<前缀>/.horsemd/manifest.json`：路径 → sha256、大小、revision（ETag），删除记为 tombstone；空文件夹记在 `dirs`。
- **本机**：`userData/sync/state/<工作区>.json`，只记**上次同步时每个文件的 sha256**，不存内容。
- **计划**（`sync-plan.js`）：以本地、云端、上次同步三方的哈希决定上传 / 下载 / 删除 / 冲突。没有上次记录又两边不同 → 冲突。
- **执行**（`sync-engine.js`）：
  - 删除先于其他操作执行，解决大小写重命名问题。
  - 下载写临时文件后改名，并校验哈希。
  - 上传带条件写（revision / createOnly）。
  - 清单最后写入，也是条件写，被别的设备抢先就失败，下次重新规划。
  - 中途停止时提交已完成的部分。
- **冲突**：原文件名保留云端版本；本机版本另存为 `x (来自 <设备名> 的冲突副本).md`，两边都有。设备名在 `sync-service.js` 里写死为 `HorseMD`。
- **回收站**：
  - 云端文件被删除或被替换前，复制到云端 `.horsemd/trash/<时间>/`。
  - 本地被同步删除的文件，移到**用户文件夹里**的 `.horsemd/trash/<时间>/`。
  - 两处都没有界面，也从不清理。
- **普通修改**：双向同步里的下载和上传都是直接覆盖，**不留旧版本**。只有一次性的「上传本地 / 下载云端」才先备份。
- **保护**：
  - 云端清单丢失或被清空且没有 tombstone 时，判定「云端被清空或替换」，停止并要求用户选方向（不会删本地）。
  - 请求节流（429 / 503 退避、数据胶囊的锁定等待）。
  - 暂停、继续、停止。
  - `.DS_Store` 等系统文件不同步。

### 1.3 本地保存和删除（同步之外，但和「数据保障」有关）

- 手动保存是 `fs.writeFile` 直接写目标文件，不是「写临时文件再改名」（`main/filesystem.js`）。写到一半断电或崩溃，文件可能损坏。这一点是读代码得出的，没有做断电实验。
- 自动保存会检查文件是否被外部改过（mtime），被改过就不写。手动保存不检查。
- 侧边栏删除文件：确认后移到系统回收站。
- 打开的文件被外部改写时：
  - 标签页没改过 → 原地重新载入；
  - 标签页有未保存修改 → 弹出提示，保留编辑器内容。

## 2. 测试结果

两个审计脚本，记录**当前**行为。它们总是以 0 退出，只报告结论：

- `node scripts/audit-sync-safety.mjs`（`--json` 输出机器可读结果）：两台设备 + 一个 S3 语义的内存云端，用的是真实的 `SyncEngine`，两台设备名都是 `HorseMD`，与实际一致。
- `node scripts/audit-sync-dirty-tab-ui.mjs`：在真实 HorseMD 里验证（带 `--horsemd-input-trace`），需先 `npm run build`。

2026-10-29 在 Mac mini 和 Windows 测试机（安装版，桌面会话）上结果一致：**8 项风险、2 项正常**（R9 当天补测）。

**P0 修复后（2026-10-29）**：审计剩 **2 项风险（R2 没有历史版本、R8 回收站），都属于 P1**；R1、R3、R4、R5、R6、R9 已修复，并写成必须通过的回归测试（见 4.P0 表的「状态」列）。mac 和 Windows 都已验证。

| 编号 | 场景 | 结论 | 实际结果 |
|---|---|---|---|
| R1 | A 有未保存的修改；B 改了同一文件并同步；A 自动同步后保存 | **丢数据** | 自动同步把 B 的版本直接写进 A 的文件。A 在应用里看到「……现在保存会覆盖外部版本」，点确定后按保存，**保存时不再提醒**，文件变成 A 的内容。再同步后，「B 的修改」在 A、B、云端（含两处回收站）**都不存在了**。 |
| R2 | 同一文件改三次，每次同步 | **没有历史** | 版本1、版本2 在任何地方都找不到。 |
| R3 | 同一文件第二次发生冲突 | **同步卡死** | 第一次冲突生成「x (来自 HorseMD 的冲突副本).md」。第二次冲突时，B 先把本地那个冲突副本改写成新内容，然后上传因同名失败（「远端文件已被其他设备修改」）。**之后 B 每次同步都失败，不会自己恢复。** 第一次的内容只剩云端那份。 |
| R4 | 一个文件被删除，另一个文件在写 | **备份被卡住** | 自动同步因为那个删除整轮不执行，正在写的文件也没有上传，只存在这台电脑上，直到用户去设置里确认。 |
| R5 | 同步扫描之后、上传之前保存了文件 | **另一台设备报错** | 清单记的是扫描时的哈希，云端存的是保存后的内容。另一台设备下载校验失败（「已在同步期间变化」），重试也失败，直到这台设备再同步一次才恢复。没有丢数据。 |
| R9 | 同步算好计划之后、写入之前，用户保存了要被下载覆盖的文件 | **丢数据** | 下载直接覆盖，刚保存的内容在两台设备和云端（含回收站）都不存在。数据胶囊限流时，计划和写入之间可能隔几分钟到二十分钟，这段时间里的保存都会被覆盖。 |
| R6 | 两台设备同时同步 | **报错（不丢数据）** | 其中一台报「远端文件已被其他设备修改，请重新同步」。用户会看到同步失败；再同步一轮后两边一致。 |
| R7 | 一边删除、另一边修改 | 正常 | 修改作为冲突副本保留在两边和云端。 |
| R8 | 回收站 | **不可见、不清理** | 本地回收站在用户文件夹里，3 轮删除后 3 个时间目录；云端 15 个对象。没有界面，没有清理。 |
| S1 | 云端被清空后同步 | 正常 | 本地文件保留；停止并提示用户选择上传或下载。 |

## 3. 业界做法（调研，2026-10-29）

调研范围：思源、Joplin、Logseq、Obsidian Sync、Remotely Save（Obsidian 插件，S3 / WebDAV，和我们最像）、Obsidian 文件恢复插件、Dropbox、OneDrive、iCloud、Syncthing、rclone bisync、Nextcloud。

大部分结论核对过官方文档或源码；标「未证实」的是没找到一手资料。

### 3.2 共同的做法

1. **普通删除和覆盖不确认，靠事后恢复兜底**：Dropbox、iCloud、OneDrive、Obsidian Sync、思源都是这样。
2. **被覆盖或删除的东西一定先存一份**：思源的数据历史、Joplin 删除前的修订、rclone 的 backup-dir、Syncthing 的版本目录。
3. **冲突两份都留，输的那份一定有地方找回**。名字里有设备和时间，方便多台设备的副本共存、看出来源。
4. **能合并就合并**：Joplin、Logseq、Remotely Save 付费版都用「上次同步时的内容」作为基线做三方合并。前提是**本机存了基线内容**，而我们只存了哈希。
5. **只在异常时刹车**：
   - 一端为空，或清单丢失；
   - 一次删除超过一定比例（rclone 50%、Remotely Save 50%、Joplin 90%）或数量（Nextcloud 100）。
   - 刹车是「暂停并说明」，不是逐个文件确认。
6. **状态安静但可见**：
   - 一个总状态（已同步 / 同步中 / 暂停 / 离线 / 出错）+ 最近同步时间 + 活动列表；
   - 自动同步只在第一次出错时弹提示（思源），手动同步总是报告结果。
7. **写入顺序**：先内容，再清单，最后指针；写入前重新检查本地有没有新改动（思源会重新扫描）。下载写临时名，校验后改名。

### 3.3 不要学的

- 按修改时间决定输赢（时钟不可靠），而且不留输的那份（Remotely Save 免费版丢过每日笔记）。
- 尽力而为的补丁合并，悄悄产生重复文字（Obsidian 官方承认）；合并结果明显变短或变空时不能静默接受（Logseq 有清空日记的报告）。
- 云端直接删除不留副本（Remotely Save）。
- 每个小文件对应一个或两个云端对象（思源没有打包）：在数据胶囊这种限制 PUT 次数（约 200 次后锁 20 分钟）的服务上，首次同步和批量修改会被锁住。
- 每次同步都完整列出云端文件（Joplin 在 S3 / WebDAV 上就是这样）；一端的设置能缩短所有设备的历史保留期（Joplin）。
- 回收站不可见、无上限（我们现在就是）；措辞模糊的「全部删除 / 保留」对话框（Nextcloud）；需要专家手动 resync 才能恢复的状态（rclone）。

## 4. 改进路线

原则：**先让一切可撤回，再去掉确认**。每一项都要有自动化测试，并在 mac 和 Windows 上验证。审计脚本里的 RISK 修好后，改成断言安全行为的回归测试。

### P0：先修会丢数据或卡死的问题（不改变产品形态）

| 项 | 做法（业界依据） | 验收 / 状态 |
|---|---|---|
| R9 下载覆盖刚保存的内容 | 写入下载（以及本地删除）之前，重新读取本地文件算哈希；与计划时不同，说明用户刚改过，**不覆盖**，转为冲突（两份都留）。被替换的本地内容先放进回收站（P1 之后进版本历史）。思源在写入前重新扫描本地，Syncthing 下载写临时名、校验后再改名。 | R9 两份内容都在 · **已完成**（`test:sync-safety`） |
| R1 未保存的修改被覆盖 | 两处一起改：<br>① 同步时，渲染端把「已打开且有未保存修改」的文件路径传给引擎，这些文件本轮**不下载、不删除**，等保存后按冲突处理；<br>② 保存一个已被外部改过的文件时不再静默覆盖。标签页本来就记着打开时的内容（共同的旧版本），磁盘上是对方的版本，编辑器里是自己的版本，可以直接**三方合并**：不重叠就保存合并结果；重叠就让原文件保留磁盘上的版本，编辑器内容另存为冲突副本，标签页切过去（见 5.1；Joplin、Logseq 的基线合并，Obsidian、Nextcloud 的「云端保留原名」）。 | R1 / R1b 两边的修改都还在 · **已完成**（`test:sync-safety`、`test:save-external-merge-ui`、`test:autosave-ui`） |

### P1：本地版本历史 + 「最近删除」（「数据丢不了」）— **已完成**（2026-10-29）

实现：`src/main/history/`（历史库 + 记录点 + 接口）、`HistoryDialog` / `DeletedFilesDialog`；测试 `test:history-store`、`test:history-ui`；审计 0 项风险。

- **范围**（用户确认）：所有在 HorseMD 里保存的文件都有历史，不只云空间（Obsidian 文件恢复、思源、Joplin、VS Code 本地历史都覆盖全部文件）。同步覆盖或删除前的版本只涉及云空间的文件。
- **存什么**：总是存「即将被替换的那一份」。
  - 保存前：磁盘上的旧内容（同一文件 5 分钟内最多一份，和 Obsidian 文件恢复一样；但一次保存删掉了 30% 以上的文字时一定存，防止误删）；
  - 同步覆盖、同步删除、恢复旧版本之前：必存。
  - 文本文件超过 5 MB 时，保存前不存；图片和附件只在同步覆盖或删除时存（单个最大 100 MB）。
  - 侧边栏删除文件时（进系统回收站），Markdown 和文本文件也在「最近删除」里留一份。
- **存在哪**（用户确认）：应用数据目录 `history/`（macOS `~/Library/Application Support/horse/history/`，Windows `%APPDATA%\horse\history\`，Linux `~/.config/horse/history/`）。
  - 内容按 sha256 寻址、gzip 压缩、相同内容只存一份（`objects/`）；
  - 每个文件一份版本清单（`index/`）；
  - 删除记录单独一份清单（`deleted.json`）。
- **保留**（用户确认）：
  - 默认 30 天（可选 90 / 365）；
  - 1 小时内都留，1 天内每小时一份，30 天内每天一份，之后每周一份；
  - 总上限默认 1 GB，超出先删最旧的；固定（永久保留）的版本不删；
  - 启动后和每记录一批后清理一次，并回收没人引用的内容。
- **估算**：真实中文 Markdown 平均 11.4 KB、压缩到 47%，每个版本约 5.4 KB；普通使用 30 天约 3 MB。
- **界面**：
  - 文件右键和命令面板「历史版本…」：按时间列出（原因：保存前 / 同步更新前 / 同步删除前 / 恢复前 / 删除前），可预览、和当前内容对比、复制、恢复、固定；恢复前当前内容也存一份。
  - 「最近删除…」：列出删除记录，可预览、还原到原位置（原位置已有文件时，另存为不重名的文件）。
  - 设置 › 通用 › 保存与恢复：保留期、已用空间（对 1 GB 上限）、清空历史；自动保存也在这里。
- **同步**：本地被同步删除或替换的文件，不再移到用户文件夹里的 `.horsemd/trash/`，而是进历史和「最近删除」；记录失败时退回原来的做法（绝不在没有备份时删除）。已有的 `.horsemd/trash/` 不动。云端回收站不变。
- **限制**：历史按文件的绝对路径记；在 HorseMD 里改名或移动时，历史跟着走；在 HorseMD 外改名后，旧名下的历史仍在，只是不会自动接到新名字上（以后可以按内容匹配补上）。

### P2：让同步无感 — **已完成**（2026-10-29，#169）

实现（全部按成熟软件的做法，见下方各条）：自动同步默认开启（思源）；保存后约 30 秒、一直写最多每 2 分钟、启动、切回窗口、每 5 分钟兜底（思源 / Joplin，2 分钟上限是数据胶囊的适配）；开启时自动保存 3 秒（Obsidian）；删除直接同步、冲突先三方合并再冲突副本（Joplin / Logseq / Obsidian）；大量删除刹车 > 50% 且 ≥ 10 或 ≥ 100、移动不算（rclone / Remotely Save / Nextcloud）；只提醒一连串错误的第一次（思源）；状态栏同步状态（Obsidian / Dropbox）；历史每 5 分钟一份（Obsidian）；扫描按大小 + 修改时间复用哈希（Syncthing / rclone）。测试 `test:sync-auto`、`test:auto-sync-ui`。

- **扫描成本**：现在每轮同步都会读出工作区里**每个文件**的全部内容算哈希（`scanLocalWorkspace`）。图片多的文件夹配上每几分钟一次的自动同步，代价会很高（读代码得出，大文件夹未实测）。改为按「大小 + 修改时间」缓存哈希，只重新计算变了的文件；判断是否变化仍以哈希为准（Remotely Save 只看修改时间和大小，出过问题）。

- 绑定云端后**默认开启自动同步**：保存后几秒、启动时、窗口回到前台时，再加定时兜底。没有变化时只读一次清单（或一个很小的指针对象），不做任何写入。空闲时逐步延长间隔。
- **删除直接同步**（来自可信的 tombstone），删掉的文件进「最近删除」；本地删除可延迟约 1 分钟再传播（借鉴 Syncthing）。
- **冲突自动处理、不弹框**：
  - Markdown 用上次同步时的内容作基线做三方合并（diff3），不重叠的修改静默合并；
  - 重叠的生成冲突副本，并把输的版本存进历史；
  - 合并结果为空或明显变短时，一律按冲突处理。
  - 本机需要保存每个文件上次同步时的内容，P1 的版本库可以直接提供。
- **只在异常时刹车**（暂停并用普通话说明，提供「恢复这些文件」和「确实要删除」两个都可撤回的选项）：
  - 云端为空或清单丢失（现有逻辑）；
  - 一次要删除超过约一半，或超过一定数量（例如 100 个）；
  - 几乎所有文件同时变化。
- **状态**：状态栏一个小图标（已同步 / 同步中 / 暂停 / 离线 / 出错）+「上次同步 14:32」。点开是活动列表，记录最近同步了什么、每条可「恢复之前的版本」，持久保存。自动同步只在一连串错误的第一次弹提示。
- **未保存内容**：自动同步开启时，建议同时开启自动保存，或者至少在同步前提醒有未保存的标签页。需要设计，避免和 R1 冲突。

### 云空间：侧边栏的第二棵树（2026-10-29 与用户确认）— **已完成**（2026-10-29）

- 实现：`SidebarPanes.jsx`（上下两块、折叠、分隔线，`localStorage horsemd.sidebarPanes.v1`）复用 `Sidebar.jsx`（`variant: 'workspace' | 'cloud'`，各自的展开状态）；状态文字与状态栏共用 `lib/sync-status.js`；云空间的文件夹以 owner `'cloud'` 再开一份文件监视（主进程每个文件夹一个监视，两个 owner 都停了才关，移出工作区时不留空隙）。测试 `test:cloud-space-ui`（mac + Windows）。
- 定下的细节：云空间标题栏只放同步状态和 +（新建文件 / 文件夹在右键菜单里）；每篇笔记不单独加 ☁，只标同步的文件夹；标签页暂不加 ☁（状态栏已有总状态）。

- **需求**：同步过的文件夹集中在一个地方，打开就能直接浏览和编辑，方便找。名字定为「云空间」（「同步区」容易被理解成同步设置或同步状态）。
- **形式**（用户确认）：侧边栏上下两块，像 VS Code 资源管理器里可折叠的分区。

  ```
  ▾ 工作区                 + 📄 📁 ⋯
    ▸ 草稿
    ▸ 读书笔记   ☁
    ▸ 项目文档
  ▾ 云空间  ☁ 2 分钟前同步    + ⋯
    ▸ 读书笔记   ☁
    ▾ 工作日志   ☁
        周报 10-29.md
  ```

- **规则**：
  - 两块的标题栏都能点击折叠；一块收起时另一块占满高度；都展开时中间的分隔线可拖动。折叠状态和高度下次打开时保持。
  - 云空间显示**所有**加入同步的文件夹，即使它不在工作区里（例如从工作区移除了，或是第二台设备从云端下载下来的）。
  - **同一个文件夹可以同时出现在两棵树里**（用户确认）。在工作区里，属于云空间的文件夹带 ☁ 标识，让用户知道它同时在云空间中。两棵树指向磁盘上同一批文件：在任一边改名、删除、新建，另一边同步更新（复用现有的文件监视）；展开状态各自独立。
  - 同步是按文件夹进行的，所以 ☁ 标在同步的文件夹上。打开的笔记属于云空间时，标签页或状态栏也显示 ☁。是否给文件夹里的每篇笔记都加 ☁，实现时看效果再定（每篇都标会比较密）。
  - 从工作区移除：只是从工作区拿掉，仍在云空间。从云空间移除：等于停止同步这个文件夹（需确认，不删除任何文件），文件夹仍可留在工作区。
  - 云空间标题栏的「+」：添加一个同步文件夹（新建或从云端已有的工作区下载）；标题旁显示总的同步状态和上次同步时间，出错时变红，点击进入同步设置。
  - 空状态：还没有同步文件夹时显示「还没有同步的文件夹 · 添加」。不支持云同步的平台（目前的移动端）不显示云空间。
- **性能**：
  - 和工作区一样按层加载，只在展开时列出那一层的文件名；文件内容点开才读；启动时不访问云端。
  - 实测（Mac mini，2000 个约 2 KB 的笔记）：列出一层约 1 ms，全部 stat 约 4 ms，全部读出并算哈希约 24 ms。
  - 同步状态从本地同步记录读取，由同步引擎推送更新。
- **以后可以加**（参考 Dropbox、Nextcloud、VS Code 的做法：状态都标在文件树上，并配一个总的状态入口）：
  - 云空间里文件的待上传、冲突、出错标记（已同步的不标）；
  - 状态栏同步图标，点开是问题、最近活动、最近删除。

## 5. 需要决定的问题（附业界做法，2026-10-29）

每题列出业界怎么做，以及据此给出的推荐。状态：**待用户确认**。

### 5.1 同步遇到「已打开、还没保存」的文件

- **业界**：
  - 成熟的笔记软件（Obsidian、思源、Logseq、Joplin）**输入即自动保存**，没有「未保存」状态，所以不会遇到这个问题。
  - 真正两边都改了时，先**自动合并**：Joplin、Logseq 以上次同步的内容为基线做三方合并；Obsidian 默认也合并 Markdown，但算法偶尔会重复文字。
  - 合不了时**云端版本保留原文件名，本地版本另存为副本**：Obsidian 的冲突文件选项、Nextcloud、Dropbox（先到服务器的保留原名）。
- **推荐**（修正了最初「编辑器内容为准、云端另存」的想法，那和惯例相反）：
  - 先尝试三方合并；
  - 合不了时，原文件保留云端版本，编辑器里的内容另存为冲突副本，标签页切到副本，用户接着写，不丢一个字。

### 5.2 版本历史存在哪里

- **业界没有统一做法**：
  - Obsidian 文件恢复：库外的应用数据，但按绝对路径记，库移动后历史就找不到了；
  - Syncthing：同步文件夹里的 `.stversions/`；
  - Logseq：库里的 `logseq/bak/`；
  - 思源：自己管理的工作区目录；
  - Dropbox、Obsidian Sync、Nextcloud：服务器端。
- **推荐**：应用数据目录（不会被别的同步工具带走或误删，用户文件夹干净）。避开 Obsidian 的坑：不能只按绝对路径记，文件夹移动或改名后历史要能接上，例如以工作区 ID + 相对路径为键。

### 5.3 保留多久、占多少空间

- **业界**：
  - 保留期：30 天是最常见的基准（Dropbox 免费版、OneDrive、iCloud）。付费版或别的产品更长：Dropbox 180 / 365 天，Joplin 90 天，Obsidian Sync 1 或 12 个月。
  - 保存频率：同一文件每 10 分钟一份（思源、Joplin），Obsidian 文件恢复每 5 分钟一份。
  - 分级保留：Syncthing、Nextcloud 都是「1 小时内密、1 天内每小时、30 天内每天、之后每周」。
  - 空间上限：Nextcloud 版本最多占可用空间的 50%。
  - 永久保留：Nextcloud 命名的版本永不过期。
- **推荐**：
  - 默认 30 天，可选 90 / 365 天；按上面的方式分级保留；
  - 同一文件每 5–10 分钟最多存一份，但同步覆盖或删除前必存；
  - 空间上限按可用空间的比例（具体比例待定）；
  - 可以把某个版本标为永久保留。

### 5.4 自动同步是否默认开启、什么时候停下来

- **业界**：
  - 默认开启：Dropbox、iCloud、OneDrive、Obsidian Sync、Nextcloud 一直同步；思源开启同步后默认每 30 秒；Joplin 改完几秒内上传。默认关闭的只有 Remotely Save。
  - 云端为空就停：rclone、Remotely Save、Joplin、思源、Syncthing 都有，是共识。
  - 大量删除的门槛不统一：rclone、Remotely Save 50%；Joplin 90%；Nextcloud 100 个文件（新版是否默认开启未核实）；OneDrive 约 700 个（未核实）；Dropbox 没找到说明。
  - 几乎所有文件同时变化就停：只有 rclone 有。
- **推荐**：绑定云端后默认开启；在云端为空或清单丢失、一次删除超过一半或超过 100 个、几乎所有文件同时变化时暂停，并说明原因。

### 5.5 自动保存是否随同步默认开启

- **业界**：Obsidian、思源、Logseq、Joplin 都一直自动保存，没有保存按钮（公认事实，不是本次调研的内容）。HorseMD 和 Typora 保留了手动保存，所以才会有 5.1 的情况。
- **推荐**：开启云同步时一并打开自动保存（停止输入约 3 秒后保存）。是否进一步改成所有用户默认自动保存，会改变现有用户的习惯，单独决定。
