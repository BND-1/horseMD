# 富文本新建列表首项合并、标记漂移与嵌套列表丢失报告

> 状态：已修复并纳入逐字、保存、完整重开和“立即切源码”回归。最后更新：2026-08-02。

## 症状

在已有正文中继续写作，或在新建文档的默认 H1 + 正文路径中按 Enter 后连续手打 `- `、`1. ` 创建列表，切到源码可能出现：

- 新列表首项被拼到上一段正文；
- 用户输入的 `-` 变成 Crepe 默认的 `*`；
- 源码出现 `- <br />`，后续保存重开后结构继续错误。
- 新建未保存文档中的有序列表、第二项或嵌套项被合成一行，甚至只剩最深层项目。
- 在嵌套有序列表中连续按 Enter 退出两层后，再手打 `- ` 创建无序列表，源码可能残留空的 `3.`、把新列表改成 `*`，或把后续文本拼进前一个列表。
- 删除无序项后继续手打 `1. ` 创建新的有序列表并再嵌套，源码可能把用户输入的 `1.` 规范成 `1)`；若回调已延迟到嵌套项，旧逻辑还可能把 marker 恢复到先前列表行，造成后续结构基线继续漂移。
- 多项有序列表和两层嵌套后手打 `- `，再按 Enter 新增同级项、Tab 创建子级：前面已正确写入的 `-` 可能在下一次回调整体退化为 `*`；快速连续输入时，外层 `-` 与自动创建的子级甚至可能在首次源码快照中一起变为 `*`。

## 根因

Enter 先创建一个空 ProseMirror paragraph；当 `- ` 触发输入规则时，Crepe 把新空 list item 序列化为带 `<br />` 的内部占位。旧保真层把该占位写入 `lastMarkdownRef`。这个空列表项没有可见文本，下一次输入使用普通可见字符映射时只能落到上一段末尾，因此把列表文字并回正文。

更隐蔽的实际竞态是：连续键入 Enter、`-`、空格时，Space 已经把 ProseMirror 转成 list，但前两次 `markdownUpdated` 还未把“空段落/转义 marker”发布到原始源码快照。此时 `lastMarkdownRef` 仍停在上一段，`pmPosToMarkdownOffset()` 会返回无意义的位置；不能再把它当成可用的文本坐标。

该输入规则意图过去又被保留 30 秒。用户继续按 Enter、Tab 创建嵌套列表时，旧的“首次建表”源码快照会错误套用到当前内层 list，覆盖已存在的外层项目。这解释了截图中富文本层级正确、源码却只剩一行或只剩内层的现象。

还必须区分“已有源码上的局部列表输入”和“新文档第一次回调”。后者可能把标题、正文、外层列表和嵌套列表全部合并到同一次 `markdownUpdated` 中；此时输入规则记录的 source/canonical 都为空，当前光标却已位于内层。若专用列表补丁抢先写入，只会写回内层，正确做法是让新文档通用路径接收完整 canonical，再仅恢复无序 marker。新建内容没有既有排版可保留时，生成紧凑列表，不能凭空插入外层—内层间空行。

同时，初始化基线通过 `crepe.getMarkdown()` 读取缓存，而保存/模式切换通过 `serializerCtx(view.state.doc)` 读取实时文档。两者可能仅在列表结尾换行不同，导致未编辑的模式切换也被误判为结构变更并重写尾部原文。

另一个独立时序边界是：按 Enter 新增同级列表项、或 Tab 自动创建子级，不会触发 `- ` 的输入规则。旧 `preserveGeneratedBulletMarkers()` 只有在源码与 canonical 的列表行数完全相等时才按 ordinal 保留 marker；新增项或“空顶层项被 Tab 替换为子级”会破坏这个条件，直接放行 Crepe 的 `*`。极快输入时，整棵列表还可能在首个 `markdownUpdated` 才一次性发布，source 基线为空；外层 `-` 被记录了，但自动生成的子级没有自己的 marker 意图。

## 修复

1. `keydown` 在 Space 进入输入规则前记录 `-` / `*` / `+` / `1.` / `1)`；`beforeinput` 仅保留给 IME/辅助输入的兜底，不能承担物理键盘的唯一时序。
2. `normalizeEmptyListItems()` 只移除空 list item 的 `<br />` 占位，保留 marker 和空格；真实 `text<br>text` 不改。
3. 若源码中已发布转义 marker，只替换那一行。若尚未发布，则以输入规则的前/后 canonical 快照和相邻的可见文本边界，插入**仅这一个新增列表**；文档末尾与正文中间都有独立路径，绝不借用上一段的零宽位置。
4. 首个列表文字输入检测到“前一 canonical list item 为空”时，按列表树在文档中的顺序定位对应源列表，再只替换该列表树；不使用零可见字符的普通段落映射。
5. 初始 canonical baseline 与强制 flush 均使用 `serializerCtx(view.state.doc)`；如果差异仅是 canonical 尾换行，保留原始源码，不把它当作用户编辑。
6. 输入规则意图只服务**首次成功创建的那一个列表**；成功重建后立即清除。后续 Enter、Tab、嵌套和继续输入一律使用新的 source/canonical 基线，不能重放旧快照。
7. 空 source + 空 canonical 的首次回调不走局部输入规则替换；保留完整新文档。若回调已经延迟到嵌套层，专用路径也必须选择该 delta 新增的**第一个外层列表**，不可依据当前 selection 选内层。
8. 新建文档的全部内容仍只来自富文本时，源码基线改为**当前完整 ProseMirror canonical 文档**，而不是把每一次延迟回调逐步拼接。原因是退出嵌套列表会短暂发布空的有序项；这个中间态没有用户源码语义，不能成为下一次增量映射的基线。此路径只在文档最初为空、且用户尚未从源码模式提交内容时启用。
9. “立即切源码”走 `flushMarkdown()`，也必须复用同一条完整 canonical 路径，并消费 Space 键前捕获的无序 marker 意图；否则 `markdownUpdated` 尚未来得及发布时，Crepe 默认 `*` 会覆盖用户刚手打的 `-`。只有用户在源码模式**实际修改后**再提交 Markdown，生成路径才关闭；纯查看/导出不会改变该判定。之后回到普通的原文保真局部映射。
10. 输入规则意图额外保存 Space 前的 ProseMirror 位置。延迟 `markdownUpdated` 到来时，当前 selection 可能早已位于后续新项或嵌套项，不能再用它推断“刚创建的是哪一行”。恢复 marker 时优先映射这个捕获位置；有序 `1.` / `1)` 只替换刚创建的一行，绝不能把同层已有的 `2.`、`3.` 改为 `1.`。
11. 生成型新文档在列表行数变化时不再直接放弃 marker 保真：仅当某一层已有唯一的 marker 风格时，新增同级项继承它；Tab 产生的 `* <br />` 被识别为内部占位而非用户选择，可继承已明确的父级风格。混合 marker 层级无法安全判断时保持 canonical，不猜测覆盖。若整篇内容在第一次回调才发布，则外层手打 `-` 的输入意图会同时覆盖这棵新 list tree 中由 Enter/Tab 自动生成的子级；已有源码路径不采用此扩展规则。

专项 Electron 回归逐字输入并在正文、Enter、`-`、空格和列表文字之间停顿，随后切源码、保存、使用全新 profile 重开并逐字符比较。每次命令同时覆盖文档末尾与“新列表后仍有后续段落”的中间插入，避免只修好末尾特例。新文档专项还覆盖默认 H1、正文、`1. ` 有序列表、第二项目和 Tab 嵌套项，并且在**未保存**状态连续切两次源码；它分别运行稳定节奏、35ms 连续键入 + 标题 Enter 进入正文的合并回调节奏、“嵌套项 → Enter ×3 → `- ` 无序项 → 不等待回调立即切源码 → 保存 → 全新进程重开”，以及“删除无序项 → 离开空列表 → `1. ` 新有序项 → Tab 嵌套 → 立即源码 → 保存重开”。另覆盖三项有序 + 两项嵌套后手打 `- `、Enter 同级、Tab 子级的完整链路，分别以普通停顿和 35ms 连续节奏执行；源码、二次切换、保存和全新重开均逐字比较。该时序不能用一次性插入或粘贴替代。
