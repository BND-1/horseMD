# 设置页排版宽度无反馈问题复盘

## 现象

在“设置 → 外观 → 排版”调整编辑区宽度时，设置值和底部文档排版实际已经更新，但设置页下方的示例看起来没有变化。字号、行距、段距等项目均有即时反馈，因此用户会合理地判断页宽控件失效。

## 根因

真实页宽的可选范围为 600–1400px，常用预设是 700、800、1000px 和全宽。设置页预览正文原先使用：

```css
width: min(100%, 680px, var(--editor-max-width, 800px));
```

固定的 `680px` 上限比所有三个数值预设都窄。无论选择 700、800 还是 1000px，最终可见宽度都会被截成 680px。原回归测试只断言：

- `horsemd.settings.v1.pageWidth` 已更新；
- `--editor-max-width` 已更新；
- `hm-full-width` 类已切换。

它没有测量预览正文的实际矩形，所以“状态正确、用户看不见”的问题未被发现。

## 修复

`TypographyControls.jsx` 现在把真实 600–1400px 页宽线性映射到预览画布的 440–680px：

- 预览仍能在设置页有限空间中完整展示；
- 窄、中、宽形成明确但不过度夸张的宽度差；
- 全宽占满预览画布；
- 预览背景与页面背景分层，两侧留白可以直接识别。

微调滑杆的 `liveApply` 同时更新真实页面 CSS 和预览专用变量。拖动期间不经过持久化状态往返，预览仍能逐帧响应；松手后再写入设置。

## 验证

自动化测试 `npm run test:settings-ui` 现在额外检查：

1. 默认、中、宽、全宽的预览正文实际宽度逐级增加；
2. 对页宽滑杆发送 `pointerdown` 后，在尚未发送 `pointerup` 时，预览宽度已经明显变化；
3. 松手后数值持久化为目标宽度；
4. CSS 变量和 `hm-full-width` 类仍与设置一致。

同时运行：

```bash
npm run test:settings-layout-ui
npm run test:editor-style-settings-ui
```

覆盖桌面、窄窗口、移动布局与六套内置主题，防止预览产生横向溢出或主题对比问题。

## 防回归约束

- 设置控件测试不能只验证 localStorage 或 CSS 变量，还要验证用户能看到的几何或样式结果。
- 预览是缩尺模型，不能直接用低于真实页宽预设的固定像素上限。
- 页宽微调必须在按住拖动时实时反馈，不能只在松手后变化。
